Session 1 · 5 min · the principle

The need-to-know principle

Press the button SG12: coffee machine

You press “espresso”. You do not need to know about the pump pressure, the heating coil, or the grind size. The machine hides how behind a button that says what.

SG12's rule: at every layer, you need to know the interface — and you need to know the layer below only if you are the one repairing it.

Same principle, everywhere

Game controller: you know the buttons, not the Bluetooth stack. Smartphone: you know the apps, not the radio firmware. Digital scale: you read the number; the load cells stay inside. SG12 key concepts

The two words this unit nails down: INTERFACE — what a thing lets you do (the buttons) · IMPLEMENTATION — how it actually works (the gears). Abstraction is leading with the interface and hiding the implementation until someone needs to know.
Teacher cue: SG12's “Digital Scale Analysis” thinking activity maps perfectly here: students list the scale's buttons (interface) versus its load cells and firmware (implementation), then label which audience needs which. Two minutes, and the vocabulary is planted for the code slides.

Session 1 · Python's abc module

Writing the promise into the language

from abc import ABC, abstractmethod

class Animal(ABC):          # inherits the rulebook
    @abstractmethod
    def make_sound(self):
        ...               # a “sticky note”, no body

# Animal is now a BLUEPRINT.
# It exists to be inherited from —
# not to be instantiated.

ABC — the base of rules

A class that inherits from ABC may declare methods that have no body — and Python then refuses to build objects from it.

@abstractmethod — the sticky note

Marks a method as “every child MUST write this.” SG12's pattern study calls it a sticky note on the blueprint — the LabApparatus example, next session.

Why not just write pass?

A plain empty method still lets users build half-finished objects. @abstractmethod turns a polite note into an enforced contract.

Teacher cue: SG12's Activity 1 (“Spot the Error!”) shows three snippets where only one is legal — keep that activity for Session 2's warm-up, it lands after slides 7–8 have shown the crash. The ellipsis ... in the sticky-note body is legal Python; some guides write pass — identical meaning.

THE RULE You cannot build a blueprint

Animal()      # try to build from the blueprint

The rule, plainly: an abstract class is a plan, not a thing.

↓
The crash is a feature: it fires the instant you try, not halfway through a game.

Session 1 · the contract — verified live

Sign it, or inherit the obligation

class Puppy(Animal):
    pass          # inherited… the OBLIGATION

Puppy()

# but sign the contract:
class Dog(Animal):
    def make_sound(self):
        return "Woof"

Dog().make_sound()
Puppy() → TypeError: Can't instantiate abstract class Puppy without an implementation for abstract method 'make_sound' — a child that does not implement the abstract method is abstract itself. The obligation is inherited like everything else. verified
↓
Dog signs the contract → instantiable → "Woof" verified
↓
The contract chain: abstract methods pass down generation after generation until SOMEONE writes a real body.
Interface vs implementation, now enforced: Animal fixed the interface (“every animal can make_sound()”); each child supplies its own implementation. The abstract base class is the interface, written in code.
Teacher cue: the Puppy crash surprises students (“I didn't even call anything!”) — construction IS the check. This is the exact shape of the engine crash on slide 11; keep this slide's wording in reach when you get there.

Session 2 · RogueEdu's core engine — the real code

Your engine already speaks ABC

# engine/base_classes.py — the real hierarchy
from abc import ABC, abstractmethod
from engine.actions import Action

class GameObject(ABC):
    @abstractmethod
    def symbol(self) -> str: ...

class Character(GameObject):
    def symbol(self) -> str:  # signs GameObject's part
        return "🧍"

class Villain(Character):
    @abstractmethod
    def act(self, view) -> Action: ...
GameObject(ABC) — abstract: {symbol}
↓
Character — implements symbol() → abstract: { } (empty!)
↓
Villain(Character) — adds @abstractmethod act → abstract: {act} all verified via __abstractmethods__
Read the chain like a contract ledger: GameObject demands a symbol; Character pays that debt and adds none; Villain is born debt-free and immediately demands act from ITS children. Your monsters pay Villain's line. base_classes.py

Session 2 · why the engine demands the contract

The ABC is the engine's insurance policy

The engine's one bet

action = villain.act(view)

The turn loop calls act() on every entry of a mixed list and trusts the answer. The ABC is what makes that trust safe: Python guarantees every entry HAS an act(), or the game never boots.

Crash at boot, not mid-game verified

Because the check fires at construction, a broken monster dies at create_game() — in your terminal, with a readable error — before any player presses a key.

Only one signature required verified

symbol() is already paid (Character implements it), so a Villain child that writes only act() is instantiable — it even inherits the generic 🧍 symbol until it overrides. act() is the one promise that matters.

Interface vs implementation, engine edition: the interface is act(view) — “every villain answers for its turn”. The implementation is each monster's private three-liner. The loop is married to the first and has never heard of the second.
Teacher cue: the Wisp proof (live): a Villain child with ONLY act() instantiates fine and shows the default 🧍 symbol — proof that Character already paid the symbol debt. Do not let students conclude “write act only” as a style rule — the deck teaches symbol overrides from C-3; this slide is about what is REQUIRED, not what is customary.

Session 2 · PREDICT — the Ghost trap

PREDICT The student and the Ghost

from engine.base_classes import Villain

class Ghost(Villain):
    def __init__(self, x, y):
        super().__init__("Ghost", x, y,
                         hp=5, attack_power=1)

# spooky… but one method is missing.
ghost = Ghost(1, 1)

A student wants a spooky monster, writes a proper __init__… and forgets act() completely. They run the game. What happens? Commit before the reveal.

The game never starts. The terminal speaks first:
↓
TypeError: Can't instantiate abstract class Ghost without an implementation for abstract method 'act' verified verbatim
↓
No traceback jungle, no half-broken save file — one sentence, naming the class and the missing method. Fix: give Ghost an act() (or run the chakra check, which says exactly this as a [FAIL] line).
The ABC turned a design mistake into a polite error message. Without the contract, the game would boot and crash MID-TURN the first time the loop asked the Ghost to move — with every player already holding the controller.

Session 2 · 2 min · key takeaways

If you remember four rules

1. Abstraction = lead with the interface (the what), hide the implementation (the how) until someone needs to know.

2. An abstract base class (ABC + @abstractmethod) is a blueprint: it can be inherited from, never built from.

3. The contract is inherited: a child that does not implement every abstract method is abstract itself — the debt passes down.

4. The engine bets its whole loop on that contract: villain.act(view) is safe because the ABC crashes impostors at boot, not mid-game.

And in the village: Villain demands act(view); every monster signs it its own way — “You decide. The engine acts.”
