1 · The problem encapsulation solves

Anything can write anything

a = Account()
a.balance = -500     # no complaint

s = Student()
s.age = -100         # no complaint

a.balance = 10**18   # sure, why not

Python trusts the caller completely. Any code holding the object can set any attribute to any value.

outside code
↓
balance = -500
↓
BAD STATE — negative balance, negative age,
reports & logic quietly poisoned
Why this is a real problem: the object cannot defend itself. Bad data enters silently and surfaces later — as a wrong report, a crash on withdrawal, a monster with negative hp. The fix is not “be careful.” The fix is putting the check inside the object.

3 · Access control in Python

Three spellings — one honest table

ConventionExampleCurriculum wording SG8Python reality verified
publicself.nameAccessible anywhereAccessible anywhere — nothing to enforce
protectedself._hp“Accessible within the same package”Writable by anyone, no error. Python has no packages-in-the-Java sense; the underscore means “internal — hands off.”
privateself.__pin“Accessible only inside the class”Plain s.__pin raises AttributeError — but the attribute is renamed (name mangling) to s._Student__pin, which still works. Discourages; does not forbid.
Honest framing (keep this all unit): in Python these are conventions signaled by symbols, not keywords enforced by a compiler as in Java/C++. The rule is real — it is a rule between programmers. Enforced protection must be built as code inside the object (getters/setters — next).

3 · Access control — predict before you see

PREDICT What does Python actually do?

class Student:
    def __init__(self):
        self.name = "Ada"
        self._hp = 50
        self.__pin = "1234"

s = Student()
s.name = "Bo"      # error?
s._hp = 9999     # error?
print(s.__pin)   # error?

Commit to all three answers before the reveal.

s.name = "Bo" → fine (public: open by design)
·
s._hp = 9999 → fine too — no error. The underscore talked to you, not to Python.
·
print(s.__pin) → AttributeError — no plain __pin exists…
…but print(s._Student__pin) prints 1234, and s._Student__pin = -100 is accepted. Renamed, not locked.
The takeaway sentence: in Python, “private” means you're not supposed to — not you can't. So where does real protection come from? Methods the class provides. That's next.

4 · Getter and setter methods

Doors in the wall — the SG8 Student class

class Student:
    def __init__(self, name, age):
        self.__name = name
        self.__age = 0          # safe default
        self.set_age(age)       # validate on the way in

    # setter — controlled write
    def set_age(self, age):
        if age > 0:
            self.__age = age

    # getter — controlled read
    def get_age(self):
        return self.__age

setter → controlled modification

The only write path. Validation lives here: if age > 0 — anything else is ignored.

getter → controlled reading

get_age() returns the value; outside code never touches __age directly.

The state + behavior bundle

The data (__age) and its guard (set_age) live together in one class — that bundling is half of encapsulation; the door is the other half.

6 · The important bridge

Same control. Cleaner interface.

Traditional interface

s.get_age()
s.set_age(15)

Explicit doors. Validation guaranteed. (Every language has this pattern — it is not “wrong.”)

⟶
@property
same guard,
new look

Python property interface

s.age
s.age = 15

Looks like ordinary attribute access — runs the getter / setter underneath. No parentheses.

The sentence that must survive this slide: @property does not remove the encapsulation or the validation — it changes the interface so that controlled access looks like ordinary attribute access. The check still runs on every write.

6 · @property mechanics

What the decorators actually do

class Rectangle:
    def __init__(self, width):
        self.width = width   # → setter runs!

    @property
    def width(self):         # getter
        return self.__width

    @width.setter
    def width(self, w):      # setter
        if w > 0:
            self.__width = w

SG8 Activity 2 rebuilds exactly this Rectangle pattern from the video resource.

@property — the getter half

Registers width so that reading r.width calls your method. “Access a method like a variable.”

@width.setter — the write half

Registers the assignment r.width = … to run your validating method. The two decorators are a matched pair sharing one name.

Scope discipline

Only these two in Grade 9. @width.deleter exists (optional extension). @staticmethod/@classmethod belong to a later unit.

Not magic — a shortcut

A property is the getter/setter pattern, rearranged. Nothing about encapsulation is lost.

6 · @property — predict before you see

PREDICT The read-only surprise

class BankAccount:
    def __init__(self):
        self.set_balance(100)
    def set_balance(self, b):
        self.__balance = b
    @property
    def balance(self):
        return self.__balance

b = BankAccount()
b.set_balance(5)   # fine?
b.balance = 999    # fine?
b.set_balance(5) → works — the setter method is the write path
↓
b.balance = 999 → AttributeError!
A @property with no matching .setter is read-only. The class author chose the doors — and here there is exactly one way in.
·
Why this matters: the property interface can make an attribute stricter than a plain attribute, not looser. Control can increase while the syntax gets cleaner.

7 · Application — SG8 Activity 3

BankAccount — the bank hired you

The requirements (SG8 Activity 3)

  • private __account_number and __balance
  • public setter methods for both
  • balance must not be negative → ignore + warning
  • getters via @property for both
  • an object using all public methods
  • a formatted balance on screen
Notice the mix: writes go through traditional set_…() methods; reads come from property getters. Both interfaces coexist in one class — that's the Activity's design choice.
class BankAccount:
    def __init__(self, account_number, balance=0):
        self.__account_number = account_number
        self.set_balance(balance)

    def set_account_number(self, account_number):
        self.__account_number = account_number

    def set_balance(self, balance):
        if balance < 0:
            print("WARNING: balance cannot be negative.")
            return              # ignore + warn
        self.__balance = balance

    @property
    def account_number(self):
        return self.__account_number

    @property
    def balance(self):
        return self.__balance

7 · Application — the verified run

What the bank actually sees

acct = BankAccount("SAV-0019", 500)

acct.set_balance(-500)
# WARNING: balance cannot be negative.
print(acct.balance)        # 500 — kept

acct.set_balance(1250.75)
print(f"Account {acct.account_number}: "
      f"PHP {acct.balance:,.2f}")

acct.set_balance(300)
print(f"PHP {acct.balance:,.2f}")   # 300.00

Reads use the property (acct.balance, no parentheses); writes use the setter methods. The format spec :,.2f gives the money formatting.

10 · Key takeaways

If you remember five sentences

1. Encapsulation bundles data with the behavior that guards it — and offers a controlled interface instead of open attributes.

2. In Python, _ and __ are conventions (the double underscore renames; nothing is a true wall).

3. Getters/setters are the doors: setters validate, getters read — the state stays valid.

4. @property keeps the doors but hides the handles: controlled access that looks like plain attributes — validation still runs on every write.

5. In RogueEdu you are the outside caller: “You decide. The engine acts.” Same boundary, running live — and the same honest limit: conventions guide people; code enforces rules.
