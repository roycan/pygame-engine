Meeting 1 · Why JSON?

Plain text that carries structure

Why this format

  • Readable — a human can open it in any editor and see the structure
  • Structured — keys and nesting, not just a wall of characters
  • Cross-platform — nearly every language reads and writes it; the standard format for data exchange between platforms and over the internet
  • Simple rules — one file extension: .json

What JSON is NOT

Not the only format — CSV (next unit), XML, and plain text all carry data too. Not a database, not a program — it is text with a shape. And not Python's own syntax: JSON has stricter rules than a Python dict (double quotes only, for one).

Retrieval check: your last two units used two other ways to move information — a library call (SG 17) and a printed graph. What can JSON carry that neither can? (Structured records — many fields, many entries, with types — storable and re-readable.)

Meeting 1 · Inside a JSON scroll

Objects, arrays, and exactly six kinds of value

{
  "missions": [
    { "mission_id": 101, "rank": "C",
      "reward": 300, "active": true },
    { "mission_id": 102, "rank": "B",
      "reward": null, "active": false }
  ],
  "village": "Cedar Hold"
}

(valid JSON — executed and parsed before this deck shipped)

The anatomy

  • Object { } — key → value pairs
  • Array [ ] — an ordered list
  • Keys — text, double quotes always

The six value types

"text" · 300 numbers · true / false · null (deliberately empty) · nested objects · arrays of anything

Strictness is the price of portability: single quotes, comments, and trailing commas are all invalid JSON — the parser refuses everything Python would tolerate.

Meeting 1 · From Python to JSON

json.dump() — write the structures out

import json

students = {
  "students": [
    {"id": 1, "name": "Alex Rivera",
     "scores": {"math": 88, "science": 92}},
    {"id": 2, "name": "Bianca Cruz",
     "scores": {"math": 0, "science": 87}}
  ]
}

with open("students.json", "w") as file:
    json.dump(students, file, indent=4)
print("Data written to students.json")

The two moves

open(..., "w") — "w" = write (creates or replaces the file). json.dump(obj, file, indent=4) — converts the Python object to JSON text and writes it into the open file.

Why indent=4? Purely for humans: four-space nesting makes the file readable in any editor. Machines don't need it; you will, the moment you inspect what was saved. (Executed: the file above is 22 readable lines.)
Watch the direction: dump = object → file · load = file → object. Dump, load — don't mix them up (dump writes, load reads).

Meeting 1 · From JSON to Python

json.load() — read the text back into structures

import json

with open("students.json", "r") as file:
    students = json.load(file)   # text -> dict

print("Student data loaded:")
for student in students["students"]:
    print(f"{student['name']} - Math: {student['scores']['math']}")
Student data loaded:
Alex Rivera - Math: 88
Bianca Cruz - Math: 0

What happened

  • "r" = read mode
  • json.load(file) parses the text and stores it in the variable — one statement, two steps
  • Nested access works exactly like your own dicts: students["students"][0]["scores"]["math"] → 88
Note Bianca's line: Math: 0. The file round-tripped faithfully — zero survived. Hold onto that fact; slides 15 and 21 show code that would destroy it.

Meeting 1 · Following the data structure

A path, not a guess — box inside box inside box

Walk the path

Open the dict → follow the key → step through the list → follow another key:

students["students"][0]["scores"]["math"]
# dict → list[0] → dict → 88

Loop the list, not the maze

One for over the list handles any length — 2 records or 2,000. Inside the loop, the path is always the same. The output on slide 8 came from exactly this loop (executed).

Map-reading rule: every [...] is a list step, every "..." is a key step. If a path fails, one of the steps isn't there — that's slide 15's territory.

Meeting 1 · Where did my file go?

Files land where the terminal stands

Working directory — the invisible address

A relative path like students.json means "beside wherever my program is running." Different terminal, different folder → different file. That's why students.json sometimes appears "somewhere unexpected": it was written exactly where the terminal stood. Colab hides this (it manages a default folder); locally, the VS Code Explorer is your folder view — open the project with File → Open Folder and run from there.

Three different "empty"s

File contentWhat json.load() does
{"characters": []}
valid, zero records		✅ loads — returns []
0 bytes (empty file)❌ JSONDecodeError — "Expecting value: line 1 column 1"
malformed (missing comma/quote)❌ JSONDecodeError — names the problem
Never expect a silent empty list from an empty file. "No data" has two meanings with two very different outcomes — a valid structure with zero records loads; a zero-byte file is broken JSON and raises. (All three rows executed before this slide shipped.)

The class's responsibility

Meeting 1 · The class workflow

Four methods, one loop: load → modify → save

__init__(self) — open the vault

Sets self.characters = self.read_json() — the archive exists the moment the object is born.

read_json(self) — file → list

Opens anime.json, json.load()s it, returns the characters list. If the file has no data → return an empty list — handle it, don't crash (slide 10's table).

add_character(self, …) — list → append

Builds one dict from the four arguments and appends it to self.characters. The object changes in memory first.

save_anime(self) — list → file

json.dump(self.characters_as_object, file, indent=4) — writes the current list back. Nothing persists until this runs.

The loop, said plainly: modify in memory → save_anime() → the file catches up → next time, read_json() sees your changes. Skip the save and your work vanishes with the program — the classic file-handling bug, and the reason this loop gets its own slide.

Meeting 1 · Filter, save, and verify

show_characters(power_level) — selection with a condition

def show_characters(self, powerLevel):
    for character in self.characters:
        if character["power_level"] >= powerLevel:
            print(f"{character['name']} - {character['power_level']}")

One loop, one condition, prints only matches — the same selection pattern as C-8's by-rank count, at the method scale. Test it twice with different thresholds: results that only work once may be an accident.

Completion conditions — Activity 1

  • anime.json created with the given records
  • class reads it via read_json() (empty → [])
  • add_character() appends dicts
  • save_anime() writes back
  • show_characters() filters by >=
  • saved under your teacher's name convention
Verify persistence: add one character → save → close and reopen → does the new record reappear? On screen is memory; in the file is proof.

ILA · Missing values are not always zero

The if not value trap — three victims, one test

if not student["math"] … treats all three as "missing":
↓ evaluated (executed)
0 → not 0 = True  ·  "" → True  ·  None → True
and if the key is absent at all…
KeyError: 'math' — the program crashes instead of deciding
Victim #1 is a real grade: a student with math = 0 — a legitimate, recorded zero — is silently thrown out as "incomplete." The data was right; the test was wrong.

The explicit check

value = student.get("math")   # no crash
missing = value is None or (
    isinstance(value, str)
    and value.strip() == "")

Executed behavior: 0 → missing? False · None → True · " " → True · absent → True.

Rule to carry: never decide "missing" from falsiness. Ask what missing means for that field, and say it out loud: absent? null? blank? — zero is a value.
© 2026 Sir Roy · source: SG 18 Activity 2 sample (`if not student["math"]…`) critiqued per teacher notes C · all evaluations executed15 / 25
ILA · One record, two copies

Identical twin or same-name stranger?

Type 1 — exact duplicate

Same key and every value equal. Two copies of one event — counting it twice inflates every total.

a == b  →  True

Safe to remove, keeping one copy — nothing is lost, because nothing differs. Report it: C-8 printed [DUPLICATE] mission 101 — identical copy removed.

Type 2 — same ID, conflicting content

Same key, different values: id 1, math 88 vs id 1, math 75. Which is true? The data does not say.

a == c  →  False

Never auto-delete and never first-record-wins — that just picks an answer for the data. Flag it for human review and keep both until someone decides. C-8's [REVIEW] branch is this rule in code.

The question before any deletion: "If I remove this record, is anything in it known nowhere else?" If yes — it's not a duplicate, it's a decision, and decisions need a person.

ILA · Same meaning, different representation

Three spellings, one village — standardize before you group

As found in the dataProblemStandardized
" Cedar Hold "invisible whitespace"Cedar Hold" — .strip()
" OPEN "spaces and capitals"open" — both .strip() and .lower()
"Cedar"abbreviation / alias"Cedar Hold" — a mapping dict

Why order matters (executed)

" OPEN ": strip alone → "OPEN"; lower alone → " open " (spaces survive!). Strip then lower → "open". One step is not the other — and a group-by on the raw string makes three groups where one exists.

The SG's own example

"Quezon City" vs "QC" vs "Q.C." — same place, three labels. Any count, average, or chart that groups by the text instead of the meaning is quietly wrong. Standardization is how a label earns the right to be counted.

ILA · Transforming data for use

Cleaning fixes lies — transformation adds use

Changing types

"450" → 450: text that must be added or compared becomes a number. Guard it: digit-strings convert, real 0 passes through untouched (executed: '450'→450, 0→0, '600'→600).

Normalizing values

Same format everywhere: dates as YYYY-MM-DD, statuses lowercase, names trimmed — slide 17's work, generalized.

Aggregating

Many records → one number: totals, averages, counts. (C-8's "open missions by rank" is an aggregation — and why its limit sentence mattered.)

Reformatting / restructuring

One shape → another: split a full name into first/last, pivot a list into a lookup dict — preparing data for the next tool's appetite.

Cleaning vs transformation, one line: cleaning makes the data true (it says what is); transformation makes it useful (it says what you need).

Meeting 2 · Find the missing information

The supplied test has two leaks — patch both

The SG's line: if not student["math"] or not student["science"]:
↓ two failure modes (executed)
Leak 1 — a real zero dies: Bianca's None is correctly missing… but a student scored math: 0 would be dropped too (slide 15).
↓
Leak 2 — a missing key crashes: KeyError: 'math' if a record lacks the field entirely (slide 15's executed result).

Your patched check

math_score  = student.get("math")
science_score = student.get("science")
missing = (any(v is None for v in (math_score, science_score))
           or any(isinstance(v, str)
               and v.strip() == ""
               for v in (math_score, science_score)))

Explicit, crash-free — and a 0 passes: 0 → missing? False (executed).

Also report, don't vanish: whatever you skip, print it with its reason — the SG's second modification. An invisible deletion is a decision nobody can audit (C-8's law 6).

Meeting 2 · Find and report duplicates

The twin hunt — compare, keep one, report both kinds

cleaned = []
seen_ids = {}
for student in self.data["students"]:
    if student["id"] in seen_ids:
        if seen_ids[student["id"]] == student:
            print(f"Removed duplicate: {student['name']}")
            continue          # exact twin — drop the extra copy
        else:
            print(f"CONFLICT: id {student['id']} differs — needs review")
            continue          # different data — do NOT pick a winner
    seen_ids[student["id"]] = student
    cleaned.append(student)

(The structure C-8 drilled — dict equality == decides which branch runs: True = twin, False = conflict. Executed both ways.)

The three obligations

  • Compare fields — id equality alone never proves twinhood
  • Keep exactly one copy of an exact duplicate
  • Report every removal with its reason — the SG requires printing them
The line not to cross: a same-id-different-data record is not a duplicate — it's an unresolved question. Auto-deleting (or first-record-wins) invents history. Flag it; a person decides. Do not use arbitrary first-record-wins deletion as your universal rule.
On the sample above: 1 twin removed (id 1, exact match), 0 conflicts.

Meeting 2 · Trust, but verify

Four numbers, one story — the audit that earns trust

Count everything you changed

Check (C-8's ledger, executed)Value
Raw records read8
Unique ids present7 (→ 1 duplicate copy)
Records with missing team1 (→ flagged, excluded)
Retained after cleaning6

8 − 1 − 1 = 6 — the arithmetic must close. If it doesn't, one of your rules ate something it shouldn't have.

The verify list

  • Open the output file — don't trust the console alone
  • Removed records were printed with reasons
  • Spot-check one normalized value (whitespace gone, type converted)
  • Re-open the raw file — still the original 8
