From lockers to family trees

Last week (SG8): encapsulation

“Keep your valuables in a locker so only the right people can open it.” Data + behavior bundled, access controlled: get_age(), set_age(), @property.

This week (SG9): inheritance

“A family tree. Parents pass down traits — eye color, height, talents.” One class passes attributes and methods down to another.

The problem inheritance solves: an Animal has a name and can eat() and sleep(). A Dog? A Bird? A Cat? Without inheritance you copy-paste the same name/eat/sleep code into every class — four classes, three copies of identical code, and a bug means four fixes. Inheritance: write it once in Animal; let the children receive it.

Definition SG9 §1.1

Inheritance is when one class (the child) gets features from another class (the parent) — attributes and methods it can use, so you don't have to write them again.

What Dog and Cat receive: the name attribute and the eat() / sleep() methods. Written once, in Animal.

Session 1 · SG9 §1.2 · Example 1 (verbatim)

Two children, zero new code

# Create the parent class
class Animal:
    def __init__(self, name):
        self.name = name
    def eat(self):
        print(self.name, "is eating.")
    def sleep(self):
        print(self.name, "is sleeping.")

# Create the child classes
class Dog(Animal):
    pass    # no new methods

class Cat(Animal):
    pass    # no new methods

dog1 = Dog("Bruno")
cat1 = Cat("Kitty")
dog1.eat()   # Bruno is eating.
dog1.sleep() # Bruno is sleeping.
cat1.eat()   # Kitty is eating.

What Python does — step by step

1. class Dog(Animal) — the name in parentheses names the parent.  2. pass = “add nothing; inherit everything.”  3. Dog("Bruno") — Dog has no __init__, so Python uses Animal's constructor and stores "Bruno" in name.  4. dog1.eat() — Dog has no eat(), so Python looks up the family line and finds Animal's.

What Python does — where it looks

Attribute lookup walks child → parent and stops at the first hit: dog1.eat → not in Dog → found in Animal → runs there. One copy of the code, shared by every child.

Verified: this exact program runs and prints Bruno is eating. / Kitty is sleeping. — the SG9 output is real.

Session 2 · SG9 §1.2 · Example 2 (verbatim)

Three generations: Person → Employee → Manager

class Person:
    def __init__(self, name, age):
        self.name = name
        self.age = age

class Employee(Person):
    def __init__(self, name, age, job_title, salary):
        super().__init__(name, age)   # parent handles 2
        self.job_title = job_title     # I handle my own
        self.salary = salary

class Manager(Employee):
    def __init__(self, name, age, job_title, salary, department):
        super().__init__(name, age, job_title, salary)
        self.department = department

m = Manager("Alice", 35, "Project Manager", 80000, "IT")
print(m.name, m.age, m.job_title, m.salary, m.department)

✅ Verified output: Alice 35 Project Manager 80000 IT — a Manager instance owns attributes from every level of its ancestry.

Manager("Alice", 35, …, "IT") — 5 facts arrive
↓
Manager keeps department, hands 4 up: super().__init__(…)
↓
Employee keeps job_title, salary, hands 2 up: super().__init__(name, age)
↓
Person stores name, age — done. The object now owns all five.
·
Why the chain matters: nobody re-wrote self.name = name in three classes. Each class handles only what is new — that's SG9's anti-duplication point.

PREDICT Delete the super() line — what breaks?

class Goblin(Villain):
    def __init__(self, x, y):
        pass   # super().__init__ was HERE
    def act(self, view): ...
    def symbol(self): return "👺"

g = Goblin(1, 1)

The engine will ask for g.name the moment it registers or draws the Goblin.

Options: (a) prints nothing  (b) prints a default name  (c) AttributeError
↓
(c) AttributeError: 'Goblin' object has no attribute 'name'
↓
Why: the __init__ that creates name and hp lives in the parent. Skip super().__init__(…) and the parent's setup never runs — the crash is just the first place Python notices. super() is how the parent's setup gets done, not a ritual.

Session 2 · SG9 §1.3 · types of inheritance

Five names — three to master now

1 · Single master

one parent → one child.
SG9 Ex1: Animal → Dog
RogueEdu: Villain → your Slime

2 · Multilevel master

a child becomes a parent.
SG9 Ex2: Person → Employee → Manager
RogueEdu: Villain → Goblin → GoblinKing

3 · Hierarchical master

one parent → several children.
SG9: Animal → Dog, Cat
RogueEdu: Villain → Slime, Coward, …every student monster

4 · Multiple  5 · Hybrid recognize only

Multiple: one child, more than one parent. Hybrid: a combination of types, in large systems. SG9 instruction: focus on the three above; these two are vocabulary — the graded assessment and Activity 2 use single, multilevel, hierarchical.

Session 2 · SG9 §1.4 · why inheritance at all

Three payoffs — one rule of thumb

1 · Code reusability

“Write once, use many times.” The parent's attributes and methods arrive in every child automatically — shorter, cleaner programs.

2 · Models real hierarchies

Animal → Dog  ·  Person → Employee  ·  Vehicle → Car. A dog is an animal — the code relationship matches the real one, so programs stay readable.

3 · Easy maintenance

Update the parent → all child classes automatically get the update. (SG9's example: split name into first/last inside Person — every child inherits the change.)

Rule of thumb to say aloud: inheritance buys you “fix it once, everywhere wins.” Ask the class: in the Person→Employee→Manager chain, how many files change if Person.__init__ changes? One. …and how many classes receive the update? All of them.

Session 4 · graded formative assessment · 40 min · SG9 §FA1

Library Management System — parent + two children + validation

The scenario SG9 FA1

  • All library materials share: title, author → parent Publication
  • Book adds number_of_pages (child of Publication)
  • Magazine adds issue_number (child of Publication)
  • Two objects of each class; display basic info for all, details for Books/Magazines
  • Validation: pages/issue must be positive — e.g. “The number of pages must be positive” (SG8's setter skill, reused!)
This is the encapsulation + inheritance combination: super().__init__ for the shared attributes, validating setters for the new numeric ones.
class Publication:
    def __init__(self, title, author):
        self.title = title
        self.author = author
    def display_info(self):
        print(f"{self.title} by {self.author}")

class Book(Publication):
    def __init__(self, title, author, pages):
        super().__init__(title, author)
        self.set_pages(pages)          # SG8 lives here
    def set_pages(self, p):
        if p > 0: self.number_of_pages = p
        else: print("The number of pages must be positive")

class Magazine(Publication):
    def __init__(self, title, author, issue):
        super().__init__(title, author)
        self.set_issue(issue)          # same pattern
    def set_issue(self, i):
        if i > 0: self.issue_number = i
        else: print("The issue number must be positive")

✅ Teaching pattern verified live: display works, set_pages(-5) prints the message and preserves state.

Key takeaways

If you remember five sentences

1. Inheritance: a child class gets a parent's attributes and methods — write them once.

2. parent = superclass = base · child = subclass = derived. class Dog(Animal) — parent in parentheses.

3. pass children already work: Dog("Bruno") can eat() because Python looks up the family line.

4. super().__init__(…) lets each class handle only what's new — skip it and the parent's setup never runs (AttributeError).

5. Single, multilevel, hierarchical — you've now built all three. And in RogueEdu, the law still holds: “You decide. The engine acts.”
