Meeting 1 · 3 min · the problem inheritance leaves behind

Inheritance hands you someone else's method

class Animal:
    def make_sound(self):
        print(self.name, "makes a sound")   # generic

dog = Dog("Bruno")
dog.make_sound()
# Bruno makes a sound   ← …that is not a bark.

SG10's own opening: the inherited method is “sometimes too general and does not fully match the child class's specific needs.” A Dog deserves “Woof”, not a shrug.

The anti-pattern

make_dog_sound() · make_cat_sound() · make_cow_sound() …

A new method name per animal. The caller must know each type to pick the right name.

Why it kills the loop

A for animal in animals: loop can call one method name. Three names = three if branches — or no loop at all.

The fix: keep the name make_sound(), change the body per child. Same door, new behavior.
Teacher cue: SG10 § Introduction gives exactly this arc — generic make_sound() → Dog “would want to change this method so it prints 'Woof'”. Ask: “who has used a method they didn't write?” — every super().__init__() from last module counts.

Meeting 1 · 15 min · Example 1 — the mechanics

Same name, same parameters, new body

class Animal:                      # parent
    def __init__(self, name):
        self.name = name
    def make_sound(self):
        print(self.name, "makes a sound")

class Dog(Animal):                 # child
    def make_sound(self):          # ← override
        print(self.name, "says Woof!")

class Cat(Animal):                 # child
    def make_sound(self):          # ← override
        print(self.name, "says Meow!")

animal1 = Animal("Generic Animal")
dog1 = Dog("Bruno")
cat1 = Cat("Kitty")
animal1.make_sound()
dog1.make_sound()
cat1.make_sound()
dog1.make_sound()
↓
Python looks in the instance's own class first — type(dog1) is Dog… found.
↓
Dog's version runs: Bruno says Woof! verified
↓
Only if the name were missing would Python climb to Animal — that climb is what animal1 does.
The invariant (SG10, keep it exact): the override keeps the method's name and parameters identical — here, zero parameters — and changes only the body. SG10: “the child's version runs instead of the parent's version”
Teacher cue: run this live if a projector terminal is available — the three printed lines are verbatim verified outputs. Diagram wording: “looks in the instance's class first” is the Grade-9 version of MRO; do not say “MRO” to students yet (it returns in the alignment slide's teacher notes).

Meeting 1 · replacement vs extension

Total replacement — powerful, and blunt

Replace — when the child is a full answer

Dog.make_sound() never needs the generic line. “Woof!” is the whole truth for a dog. Nothing of the parent's body is worth keeping. Total replacement is correct here.

Replace — when it throws work away

Imagine the parent's method also printed a header, validated data, or displayed title and author. A child that rewrites the whole body must copy that logic — and when the parent improves it, every copy silently drifts out of date.

The cooperative move: override the method, and inside it, call the parent's version first — super().make_sound()-style. You get the parent's work plus your addition, with zero copy-paste. That is super() — SG10 Example 2, next.
Teacher cue: this slide is the bridge between SG10's Example 1 and Example 2 — the guide teaches replacement first, then super(); keep that order, students need to feel the duplication cost before the cure.

Meeting 1 · 25 min · Example 2 — extending with super()

super() — build on the parent, don't copy it

class Publication:                # parent
    def display_info(self):
        print("Title:", self.__title)
        print("Author:", self.__author)

class Book(Publication):          # child
    def display_info(self):
        super().display_info()   # parent's work first
        print("Number of Pages:",
              self.__number_of_pages)

class Magazine(Publication):      # child
    def display_info(self):
        super().display_info()   # same door
        print("Issue Number:",
              self.__issue_number)

What super() is

A built-in that calls the parent's version of the same method from inside the child's override. You have already met its sibling: super().__init__() in the last module.

The pattern

Parent part first, child part after — the call order is the display order. Each child adds exactly one line and inherits the whole base display.

Verified result live

Title: Dune
Author: Frank Herbert
Number of Pages: 412

One call — parent lines and child line.

Bug check: a student writes display_info() but forgets the super().display_info() line. What comes out — error, or something quieter?
book.display_info() → Book's override starts
↓
line 1: super().display_info() — jump UP to Publication → prints Title: Dune, Author: Frank Herbert → return
↓
back DOWN in Book → prints Number of Pages: 412
↓
Forget super() → no error, no jump — output is only Number of Pages: 412. The parent's lines silently vanish. verified
Reading order = execution order: whatever super() prints appears exactly where the call sits. Move the call to the bottom, and the child's line prints first.

“You decide. The engine acts.”

One call site, every villain engine: core.py

The engine's turn loop calls the same method name on every actor — Slime, your Shadow, any custom beast — and each object's own class decides what runs. That is this unit's concept, powering a whole game.

Bridge · code study — default chase vs specialized AI

Override half, inherit half

# student_starter/classes.py — verbatim
class Slime(Villain):
    def act(self, view):
        dx, dy = view.get_direction_toward_hero(self)
        if view.distance_to_hero(self) == 1:
            return AttackAction(dx, dy)  # adjacent: strike!
        return MoveAction(dx, dy)        # otherwise: creep closer.

The chase every RogueEdu villain is judged by — a concrete parent behavior.

class CowardGoblin(Slime):
    def act(self, view):
        if self.hp * 2 < self.max_hp:   # wounded?
            dx, dy = view.get_direction_toward_hero(self)
            return MoveAction(-dx, -dy)  # flee!
        return super().act(view)   # brave: Slime's plan

New behavior when hurt, inherited behavior when brave — super() inside a conditional.

full hp → AttackAction(dx=1, dy=0) — the super() branch: Slime's chase & bite
wounded (hp 4/10) → MoveAction(dx=-1, dy=0) — the override's own flee
The engine can't tell the difference. Its one act() call site drove both turns — logged CowardGoblin moves to (2, 3) when brave and CowardGoblin moves to (2, 4) when wounded. Uniform call, distinctive behavior. verified in-engine
Teacher cue: CowardGoblin extends Slime, not Villain — the planning draft proposed CowardGoblin(Villain) with super().act(view), but an abstract parent has no body to delegate to; that call raises NotImplementedError. Subclassing the concrete Slime makes the conditional-super() pattern real (and its __init__ takes (x, y) only — rename afterwards with self.name = "CowardGoblin"). The two outputs and both engine log lines were produced by a live run.

Meeting 2 · implementation walkthrough

One validated setter, two honest overrides

class Patient:
    def __init__(self, name, bill_amount):
        self.__name = name
        self.set_bill_amount(bill_amount)  # validate on the way in

    def get_name(self):        return self.__name
    def set_name(self, name):  self.__name = name

    def get_bill_amount(self):
        return self.__bill_amount
    def set_bill_amount(self, amount):
        if amount > 0:                 # encapsulation guards
            self.__bill_amount = amount

    def calculate_bill(self):          # the method to override
        return self.__bill_amount      # full bill: no discount
class SeniorPatient(Patient):
    def calculate_bill(self):
        return self.get_bill_amount() * 0.80

class PhilHealthPatient(Patient):
    def calculate_bill(self):
        return self.get_bill_amount() * 0.85

patients = [Patient("Juan Dela Cruz", 15000),
            SeniorPatient("Lola Maria Santos", 15000),
            PhilHealthPatient("Juanita Reyes", 15000)]
for p in patients:
    print(f"{p.get_name()}: PHP {p.calculate_bill():,.2f}")
Money formatting (CS 2 review): :,.2f = thousands separator + exactly two decimals → PHP 12,750.00, never PHP 12750.0.
Teacher cue: the children read state through the getter — and they must: inside SeniorPatient, the spelling self.__bill_amount would be name-mangled to _SeniorPatient__bill_amount, which does not exist. Encapsulation forces the clean design: the discount computation goes through the door. Overrides change the computation; the guarded data stays guarded.

Meeting 2 · common pitfalls & traps

Three ways an override silently isn't one

1 The typo

def make_sand(self):
    print(self.name, "says Woof!")
No error — Python sees a brand-new method. dog.make_sound() falls through to the parent: Rex makes a sound. Wrong behavior, zero crash. verified

2 The signature mismatch

def make_sound(self, times):
    print(self.name, "says Woof!", times)
Different parameters = a different contract. The loop's zero-argument call now breaks: TypeError … missing 1 required positional argument: 'times'. verified

3 The self-recursion

def make_sound(self):
    self.make_sound()   # meant super()
self.make_sound() calls this same override — forever: RecursionError: maximum recursion depth exceeded. The parent is reached only via super(). verified
The shared lesson: an override is a promise about a name — spell it identically, keep the parameters identical, and reach the parent only through super(). Break the promise and Python does not stop you; it just runs something else (or nothing at all).
Teacher cue: all three demos run in under a minute each and are worth the minutes — pitfall 1 especially, because nothing crashes. Ask after the typo demo: “what would the chakra-check habit catch here?” (reading expected output against actual output — evidence over vibes).

Meeting 2 · 2 min · key takeaways

If you remember five rules

1. Overriding specializes behavior while keeping the interface constant — same door, new room.

2. The method name and parameters must match the parent — or Python quietly treats it as a different method.

3. Total replacement overwrites the parent logic — right for “Woof!”, wasteful when the parent's work still matters.

4. super().method() extends: parent's work first, your addition after — build on it, never copy it.

5. In RogueEdu and in real software, overriding lets an engine treat all entities uniformly while each one acts distinctively — “You decide. The engine acts.”

Can you: state the two things an override must keep identical? · predict the output when super() is forgotten? · write the wounded-branch of a CowardGoblin.act()? · format 12750 as pesos with centavos? · say why SeniorPatient reads its bill through the getter?
