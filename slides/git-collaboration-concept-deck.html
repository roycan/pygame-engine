1 · Why sharing code isn't enough

"I pushed it — trust me."

Author pushes attack_power = 99
commit message: "truly dangerous"
↓
The engine clamped it to 40 — loudly:
[WARN] attack_power=99 is out of range [0, 40]; clamped to 40.
↓
The claim was false — and nobody had looked.

What sharing gets you — and what it doesn't

  • Sharing (push) delivers your code to a shared place — that is all it does
  • It does not check the claim in your commit message
  • It does not ask whether the change is appropriate, only whether Git can store it
  • Verification is a separate act — and it needs a second pair of eyes

2 · Pull versus Pull Request

A command — and an invitation

`git pull` a Git commandPull Request a GitHub feature
What it isAn action that immediately fetches and merges remote changes into your local branchA proposal to merge your branch — it changes nothing until reviewed and merged
DirectionRemote → your machineYour branch → the same repo's main (squad teams)
Who actsYou, alone, whenever you likeAn author proposes; reviewers judge; an integrator merges
PurposeSynchronize your copyEnable review, discussion, and approval before history changes
Two PR worlds — know which one you're in: SG 14's table describes the fork world ("an administrator pulls from your repo into their main") — that's open source. Squad teams live in the shared-repo world: one repo, your branch proposes into its main, teammates with write access do the reviewing. Same button, different village.

3 · Understanding the PR process

Anatomy of a proposal

OPENING A PR (VS Code extension or web)
base:   main          # where you propose to land
compare:feature/slime-stats  # what you propose

TITLE   stats: make the slime dangerous

DESCRIPTION
What it changes: Slime attack 99.
Why the village wants it: truly dangerous.

[ Create Pull Request ]

Base ← compare: read it as "what → into where." Wrong base = the proposal asks to land in the wrong village (close it, reopen — nothing is lost).

The branch — private until proposed

Your commits live on feature/…. The PR does not move them; it advertises them.

The title — one honest line

The next reader triages your work from this line alone. Formula: area: what changed.

The description — a CLAIM, not a report

"Truly dangerous" was a claim. The reviewer's job is to test claims against evidence — which is why the description matters even though one squad mate wrote it jokingly.

What a PR is NOT

Not a pull · not a merge · not a backup — an invitation to judge.

3 · The PR process — what the review enforces

A review needs a standard, written before the attempt

📋 Mission G-2's Design Requirement — read it as the reviewer's ruler:
"Make the Slime moderately stronger while keeping it playable and within the engine's supported limits. Your implementation must pass the checks without warnings."

Every word is checkable

  • Moderately stronger — numbers you can reason about (3 → 6: harder, winnable)
  • Playable — the starter game must remain winnable on the board
  • Within limits — hp in [1, 200]; attack_power in [0, 40]
  • Without warnings — the chakra check prints 0 warnings
The argument the standard kills: *"But 40 is inside [0, 40] — the slime IS more dangerous!"* In-range is not the requirement. A 40-damage bite downs the 25-hp starter hero in one hit — legal, and unwinnable. The clamps tell you what the engine tolerates; the requirement tells you what the village decided.

Reading the actual diff — not the description

What a review is SG14

Checking someone's code before it is accepted — catching errors, improving quality, keeping the village's standards.

What a review is NOT

Not spell-checking the commit message · not skimming the description · not rubber-stamping a friend. SG 14 calls it "code review" for a reason.

The reviewer runs it too

⚖️ Chakra check on the branch — the reviewer collects the same evidence the author sees: the [WARN] … clamped to 40 line. Two machines, one truth.

4 · Code review — the reviewer's rubric

Five checks, in order

1 · Design requirement. Moderately stronger, playable, within limits, without warnings — does the change satisfy the standard written before the attempt?

2 · Valid ranges. hp in [1, 200], attack_power in [0, 40] — inside, honestly?

3 · Warnings. Quote the chakra output line — verbatim. A WARN is public evidence, not a private feeling.

4 · Game behavior. Will the board show what the claim says? (Predict it — then the squad verifies by playing.)

5 · Readable. Would the next shinobi understand this line without asking?

Why "in order": requirement first — a change can pass checks 2–5 and still fail the mission. Technical correctness is not the same as an appropriate gameplay decision. The reviewer owns both questions.

4 · Constructive feedback

Request changes — with evidence, on the line

review comment on classes.py, line 54:
[WARN] 'Slime' had a stat clamped:
attack_power=99 is out of range [0, 40];
clamped to 40.

"The engine refuses your number and
tells everyone. The mission 'truly
dangerous' fails -- 40 downs the 25-hp
hero in one hit. Propose values inside
[0, 40] -- and honestly."

Finish review → Request changes

Evidence, quoted verbatim

The reviewer's power is not opinion — it is the same warning the engine printed, on the reviewer's own machine. Two machines, one truth.

Aimed at the work, not the person

"This claim fails" — never "you failed." The next commit is the author's answer, and the village expects one.

Request changes ≠ rejection

It means: not yet, like this. The PR stays open; the author answers with a commit. In G-2 the fix took one line and one push.

4 · The review–fix cycle

One PR, two passes — the loop that lands honest work

author: change + commit + push → open PR: the claim → reviewer: evidence → Request changes → author: fix commit to the SAME branch → PR updates itself → reviewer: re-check → Approve 🌀 → merge (merge commit) → squad pulls → verify

Verified numbers from Mission G-2 flashback

Attempt 1: attack_power=99 → WARN, clamped to 40 · Request changes with the quoted warning · Attempt 2: hp=14, attack_power=6 → 3 passed, 0 warnings → Approved. One line, one push, same branch — the PR did the ceremony for you.

Why the fix goes to the same branch

The PR is the branch's proposal. New commits on that branch join the same review — history stays one story: attempt, evidence, answer, stamp. New PR per fix would scatter the conversation.

5 · Merge conflicts — the only reliable recipe

Genuinely overlapping, incompatible changes

The recipe verified in Mission G-2

  • Two shinobi branch from the same main
  • Both rewrite the same line of the same file — the Elder's warning
  • Scroll 1's PR merges first (it may fast-forward — normal)
  • Scroll 2's PR now cannot merge: main's line changed under it
The honest boundary: G-1's two shinobi edited two different files — different lines of one file merge automatically, different files cannot collide on a line. Conflicts need overlap. That is why Mission G-1 never met one, and G-2's ILA invited one on purpose.

↓ two branches, one line
scroll 1: "The walls hold, but the slimes bite hardest…"
↓ merges first — lands cleanly
scroll 2: "Two slimes now guard this grove…"
↓ against the NEW main

5 · Resolving — both scrolls survive

Keep both ideas in one coherent line

# on the FEATURE branch
git fetch origin
git merge origin/main
# → conflict markers appear in the editor

# replace the WHOLE marker block with one
# line that keeps both ideas:
    "The walls hold, traveler, and two
     slimes now guard this grove -- they
     bite hardest at your corners!"

git add classes.py
git commit -m "merge main: keep both
  warnings -- walls hold AND two slimes"
git push          # the PR updates itself

Verified final line, spoken by the Elder in the merged game: "The walls hold, traveler, and two slimes now guard this grove -- they bite hardest at your corners!"

The anatomy of a good resolution

  • All three marker lines gone — any survivor means the fight is still on
  • Both ideas present — walls AND slimes, not one erased
  • One coherent sentence — the Elder must still sound wise
  • Chakra check green — then commit, push, re-review
Escape hatch: drowning mid-resolution? git merge --abort restores your branch cleanly — read the map, then try again. Aborting is not failure.

5 · Two warnings that are NOT the same

PREDICT Which of these is a conflict?

A. VS Code says: "Please clean your repository working tree before checkout."

B. A merge stops with: "CONFLICT (content): Merge conflict in classes.py" and markers appear.

Both stop you. Both sound scary. Are they the same problem? SG14 mentions A

A = uncommitted changes. Your own unfinished work would be disturbed by a branch switch. Commit it or discard it (↩) — a guard, not a fight. Nothing is broken.
↓
B = a merge conflict. Two already-committed histories disagree on the same lines. A human must judge — that is real collaborative work, not a mess.
·
Keep them separate: one is about your envelope being open; the other is about two sealed histories disagreeing. SG 14 names both — Mission G-2 made you live both.

6 · Recovery — your uncommitted work

Four mistakes, four quiet fixes

# 1 · ruined a tracked file? throw the edit away
git restore classes.py          (↩ Discard)

# 2 · staged the WRONG file? un-open the envelope
git restore --staged game_config.py  (− icon)

# 3 · deleted a tracked file? history still has it
git restore classes.py

# 4 · need an OLDER committed version?
git log --oneline -6            # find the good hash
git restore --source=<hash> game_config.py

All four verified in Mission G-2's drills. VS Code equivalents in parentheses — the words change, the act doesn't.

What recovery touches

Your uncommitted or local work only. Nothing shared, nothing on GitHub, nothing in a teammate's machine. Private, silent, instant.

Why history protects you

Every commit is a checkpoint Git can hand back. Deleted a tracked file? Committed history is the undeletable backup. The only truly lost work is work never committed.

The boundary sentence: recovery fixes your messes quietly. Rollback (next) fixes the village's — loudly.

6 · Rollback — undoing SHARED work

Revert: a new scroll, never an erased one

Wall PR merged: 6 pillars — the grove path is blocked
↓
The village regrets it → Revert button on the merged PR
↓
GitHub proposes a new revert PR — proposing the undo
↓
Stamped, merged, pulled → 5 pillars, game as designed
↓
History shows: merge … then Revert "…" — both kept

Why a new commit — not deletion

Every teammate's clone already holds the shared history. Erasing it would orphan every copy. A revert adds the correction on top — everyone heals by pulling. Verified: 6 walls → revert → 5 walls, `Revert "…"` in the log.

The wall between the two arts

Recovery = your uncommitted work — private, silent. Rollback = already-shared work — public, loud, a new commit for the whole village.

Never git reset --hard on shared work — it rewrites the village's memory and orphans every clone. Recovery drills are for local work; revert is for shared work.

Key takeaways

If you remember five sentences

1. A PR proposes; it does not pull, and it does not merge — it is an invitation for the village to judge.

2. A review reads the diff and collects evidence — a quoted warning beats a confident claim, every time.

3. "Request changes" is not a wall — on our private repos the Stamp Law is the wall, and the shinobi are its bricks.

4. Conflicts need overlap — resolve them on the feature branch, keeping both ideas in one coherent line; recovery fixes your quiet messes, rollback reverts shared work as a new commit — never erase the village's memory.

5. A clean merge, a green check, and a stamped PR are still not proof — the last arrow of every workflow is: run the game.
