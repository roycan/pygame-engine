2 · What version control is

A complete copy of the project and its whole history — on every machine

Version Control System SG13 wording

A tool that tracks and manages changes to source code over time. You can look back at previous versions, undo mistakes, and see who changed what.

Distributed (DVCS) SG13 wording

Every developer has a complete local copy of the entire repository — including its full history. Work offline; the network is only needed to sync.

Why bother? (SG13)

  • History — every past version is retrievable
  • Collaboration — many people, one project, no overwrites
  • Revert — go back to the last known-good version
The village archive analogy: every shinobi carries a complete copy of the archive — scrolls and all. The village hall keeps the shared copy. The analogy is the on-ramp; the machinery is real: Mission G-1 put a full clone on all three machines verified — git log showed the same history everywhere.

5 · The basic workflow — four stages

Where every change stands

1 · Working directory

Where you edit files. Saved work lives here — and no history has happened yet.

→
git add
stage

2 · Staging area

The prep zone: you choose which changes go into the next commit — the envelope.

→
git commit
record

3 · Local repository

Permanent history on your machine. The commit is a checkpoint, with a message and a hash.

→
git push
upload

4 · Remote repository

Shared history on GitHub. Now teammates can pull your checkpoint into their machines.

The first three stages live on your computer SG13 — only push touches the network. Mission G-1 map: working folder → the Staged list in VS Code → git log → the squad repo on GitHub. Analogy: write the scroll · seal the envelope · file the checkpoint · send it to the hall.

↓

6 · The core operations

Six commands, one honest table

CommandWhat it does SG13ScopeG-1
git cloneCreates a complete, fresh local copy of a repository — full history, not a ZIPRemote → LocalPhase 1
git addAdds changes from the working directory to the staging areaLocalPhase 3 · the +
git commitRecords a snapshot of staged changes into local history, with a messageLocalPhase 3
git pushUploads local commits to the remote so others can see themLocal → RemotePhase 3–4
git pullFetches remote changes and integrates (merges) them into your local branchRemote → LocalPhase 4–5

Teacher note (modern alternatives): checkout does two different jobs — switch branches and restore files. Modern Git splits them: git switch for branches, git restore for files. 8 · Meeting 1 — key takeaways

If you remember five sentences

1. A VCS tracks and manages changes; a DVCS gives every developer the full project and its whole history — offline work included.

10 · Main branch versus feature branches

The official game — and the training paths

main — the village's official game

The project's official version SG13 — the one the sensei clones, the one that must always run. In Mission G-1, only the Scout touched main, on purpose.

feature/… — the training paths

Independent lines for new features and fixes SG13. G-1 grew feature/elder-lore and feature/second-slime — in private, from main.

The honest mental model: a branch is just a movable name pointing at a line of work — not a copy of files. That is why creating one is instant and why switching branches changes your folder so dramatically. Naming law: feature/<what-it-does> — the name should tell the next reader what grows there.

10 · Creating, switching, and publishing branches

Grow a path — then let it fly

# what VS Code does for you
git switch -c feature/elder-lore  # create+switch
git switch main                   # go back
git push -u origin feature/elder-lore

# names you saw in the merge picker
  feature/elder-lore      # local only
  origin/feature/second-slime # on GitHub

local vs remote branches: your branch exists on your machine the moment you create it — Publish Branch (the cloud button) sends it to GitHub and creates the origin/… twin. Phase 4's merge picker showed both kinds.

In VS Code — your actual workflow G-1

Status bar (bottom-left) → branch name → Create new branch… → type the name → you are there. Switch the same way. Publish Branch after the first commit.

Why create from main?

A new branch grows from where you stand. Phase 2 stood on main — so both features carried main's known-good game. Branch from the line you intend to extend.

Teacher note: checkout historically did switching and restoring; SG13's table says so. Modern, focused verbs: switch (branches), restore (files). See slide 8.

12 · What happens when two developers contribute?

Two shinobi, one scroll line

same import line, two proposals:

<<<<<<< HEAD
from student_starter.classes import (
    BraveKnight, Elder, GroveElder, Slime)
=======
from student_starter.classes import (
    BraveKnight, Elder, GuardSlime, Slime)
>>>>>>> origin/demo/b

A merge conflict: Git refuses to guess. It shows both versions and asks a human to decide. Resolving is normal, planned work — SG 14 meets one on purpose.

Why G-1 had none design honesty

The two shinobi edited two different files — different lines of the same file merge automatically; different files cannot collide on a line. That made conflicts unlikely — not impossible. Off-territory edits can still collide.

Not every warning is a conflict

“Please clean your repository working tree before checkout” SG13 = uncommitted changes blocking a switch. Nothing is broken — commit or discard, then move. A guard, not a fight.

Keep the distinctions separate: uncommitted changes (your envelope is open) ≠ merge conflict (two sealed histories disagree on the same lines).

15 · Key takeaways

If you remember five sentences

1. Saving is not committing. The M badge means "changed since the last commit" — history hasn't moved.

2. Staging chooses, committing records. The Staged list is the envelope; the commit seals it into local history.

3. Committing is not pushing, pushing is not updating. Teammates' machines change only when they pull — fetch + integrate.

4. Branches work in private; merges combine in public. A merge commit has two parents — and a clean merge is not proof of a working game.

5. Every machine carries the whole history. That is what "distributed" means — and why Mission G-1 could prove the same hash on all three machines.

Appendix B · SG13 §1.1 — setup and configuration

The four steps behind every Git machine

# 1 · install Git  (git-scm.com)
# 2 · set your identity — once per machine
git config --global user.name  "Your Name"
git config --global user.email "you@example.com"
# 3 · get a repository
git clone <url>        # from a remote
git init               # or start fresh here
# 4 · connect & explore
git remote add origin <url>
git help everyday      # the daily commands

Prerequisites: VS Code installed · GitHub account — students should claim the GitHub Student Developer Pack (education.github.com/pack).
