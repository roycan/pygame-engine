Meeting 1 · 10 min · the word itself

Poly = many · Morph = form

The core idea SG11

“Polymorphism allows the same name to do different things depending on what you give it.” SG11's own analogy: the command is the same — play — but you play a song, play a movie, play a game. One word, three behaviors.

In Python: different objects responding to the exact same method call in their own unique way.

# polymorphism even WITHOUT classes — len()
print(len("Hi"))         # 2  → counts CHARACTERS
print(len([1, 2, 3]))   # 3  → counts ITEMS

# same function name, two behaviors,
# chosen by the OBJECT it operates on
You have been using polymorphism since Week 1 — every built-in that works “differently depending on the object” is this same idea wearing a uniform. verified: 2 and 3
SG11's definition, keep it exact: “Polymorphism in Python allows the same method, function, or operator to behave differently depending on the object it operates on.” One way to achieve it: inheritance + method overriding — the two units you just finished.
Teacher cue: SG11 leads with the Play analogy and built-in len()/max() before classes — keep that ramp. Ask for one more everyday overloaded word (“run”? “open”?) before touching code.

Meeting 1 · 25 min · polymorphism through inheritance

One loop, three animals

class Dog(Animal):
    def make_sound(self):
        print(self.name, "says Woof!")

class Cat(Animal):
    def make_sound(self):
        print(self.name, "says Meow!")

class Lion(Animal):
    def make_sound(self):
        print(self.name, "roars loudly.")

zoo = [Dog("Bruno"), Cat("Kitty"), Lion("Simba")]
for animal in zoo:
    animal.make_sound()
the loop knows one thing:
“everything in here is an animal”
↓
Bruno says Woof!
↓
Kitty says Meow!
↓
Simba roars loudly. verified
↓
Three overrides, one method name, zero if statements.
This is the SG10 zoo, finished: overriding gave each child its own make_sound(); polymorphism is what happens when the loop uses it. SG11: “Python chooses the right version based on the object's type.”
Teacher cue — expected answers: the three verified lines above, in list order. Bridge from last unit: overriding built the differences; polymorphism is the free lunch the loop gets because of them.

Meeting 1 · 20 min · Python reality — duck typing

Python never asks for your family tree

Two languages, two rules

  • Java/C++: the list must be declared Animal[] — no family tree, no entry.
  • Python: the loop calls animal.make_sound() and the only question asked is “does THIS object have a make_sound()?” If yes — it runs.
“If it walks like a duck and quacks like a duck, it's a duck.” Behavior is the membership test — not the classname. Python reality
class Car:
    def move(self): print("The car drives on the road.")
class Boat:
    def move(self): print("The boat sails on water.")
class Drone:
    def move(self): print("The drone flies in the sky.")

def start_trip(vehicle):
    vehicle.move()          # no type check. ever.

for v in [Car(), Boat(), Drone()]:
    start_trip(v)

No shared parent. Three strangers that all “quack” move() — one loop drives all three. verified live SG11 Activity 2

Teacher cue: this is SG11 Activity 2's exact lab (Car/Boat/Drone + start_trip), verified live: the three lines print in order. The deep cut for fast finishers: a GovernmentSubsidy object with only get_name()+calculate_bill() sails through the hospital billing loop — verified: DOH Subsidy: PHP 0.00. Duck typing needs NO inheritance at all; inheritance just guarantees the quack.

The ultimate example — RogueEdu

How would you move the enemies?

# the nightmare version — a type check per breed
for enemy in enemies:
    if type(enemy) == Slime:
        enemy.chase_and_bite()
    elif type(enemy) == Shadow:
        enemy.strike_from_the_dark()
    elif type(enemy) == CowardGoblin:
        if enemy.hp * 2 < enemy.max_hp:
            enemy.run_away()
        else:
            enemy.chase_and_bite()

Why it's a nightmare: the AI lives in the loop, not in the monster. Every new villain means editing the engine — and every edit risks breaking the breeds that already worked.

RogueEdu's engine loop — the polymorphic truth

One call site, every monster

# engine/core.py — the villain phase (condensed, real)
for villain in self.villains:
    if not villain.is_alive():
        continue                # the Dead-Actor rule

    view = self._build_view()
    action = villain.act(view)   # ← THE polymorphic call
    # then the engine dispatches on the
    # RETURNED INTENT (Move/Attack/Wait)…

self.villains is a mixed list — Slime, Shadow, Coward Goblin, whatever Week 8 adds. The engine calls act(view) on each object and never asks which breed it is.

What “doesn't know” means — precisely

The engine never type-checks the entity. It does inspect the returned intent — isinstance(action, MoveAction) etc. — because the referee must know which wish it is granting. Checking the wish is fine; checking the wisher is the nightmare.

You decide. The engine acts.

Each monster returns its own intent from its own act(); the loop validates it, refuses illegal wishes loudly, and applies the legal ones. Same call site since Week 1.

party = [Slime(5, 5), Shadow(5, 5),

Round 1 — healthy: all three return AttackAction(dx=1, dy=0) — the bite. Three classes, one answer. verified

Round 2 — the same wound lands on all three…
↓
Slime: AttackAction — keeps biting · Shadow: AttackAction — keeps striking
↓

Why this makes software scalable

Add a hundred monsters. Touch zero engine lines.

The proof already happened

  • Mission C-3: Shadow joined the board — a new class, pasted at the bottom of classes.py, registered on one line.
  • Mission C-4: Coward Goblin joined — again, no engine edit.
  • The turn loop, the collision math, the combat rules: unchanged since before either mission.

The deal, in one sentence

The engine keeps calling act(); every new monster answers for itself. New behavior ships as a new class, not as an edit to working code.

Meeting 2 · common pitfall — the missing method

Duck typing fails loudly

from engine.base_classes import Wall

w = Wall("Rock", 0, 0)
w.act(view)     # a Wall in the villains' role
AttributeError: 'Wall' object has no attribute 'act' — Python tried the call and the quack wasn't there. No inheritance, no override, no fallback. verified

The engine checks at the door too

Putting that Wall into the roster is refused on arrival: TypeError: add_villain expects a Villain subclass, got Wall. Duck typing trusts the call; the referee still checks the roster. verified

The takeaway: polymorphism moves the type check from before the loop (Java's Animal[]) to the moment of the call (Python's AttributeError). It is not “no rules” — it is rules at runtime.
Teacher cue: both failures verified live. Link back to C-4: the goblin whose override was named get_action silently never fled — the missing method hid because the concrete parent still answered. A Wall can't hide: it has nothing to inherit.

Meeting 2 · 2 min · summary & shinobi rules

If you remember four rules

1. Polymorphism treats different objects uniformly through one shared method name.

2. It stands on inheritance and overriding — the differences were built in the last two units.

3. Python uses duck typing: the method is assumed to exist and checked only at the moment of the call.

4. That is how engines and big systems scale — new kinds of objects arrive as new classes, never as new if/else chains in working code.

And in the village: the loop says act(view); the slime bites, the shadow strikes, the goblin runs — “You decide. The engine acts.”
