Meeting 1 · The language of reusable code

Four words, one ladder

Module — one file

One .py file with functions inside. math is one you will meet today.

Package / library — a kit of files

Many modules bundled, installable, versioned. matplotlib is one; "library" and "package" are used interchangeably at this scale.

Framework — a kit that runs the show

Flask (the engine under RogueEdu) doesn't wait to be called — it calls your code when a request arrives. More on the next slides.

Package manager — the delivery truck

pip fetches kits from an online store (for Python: PyPI) and installs them into your project. You never download zip files by hand.

Meeting 1 · Library or framework?

Who calls whom?

Library — you call it

Your program decides when: plt.plot(...) runs because you wrote it on that line. A tool you pick up and put down.

Framework — it calls you

A request arrives — Flask runs your function. You built the room; the framework decides when it is used.

You have lived this difference: in RogueEdu you write act() — and the engine calls it every turn. "You decide. The engine acts." That is framework thinking. matplotlib, in Mission L-1, is the other kind: your line of code summons it.

Meeting 1 · Built-in tools vs downloaded tools

Not all libraries need a truck

Standard library — ships with Python

import math — done. math is already on your machine inside Python itself: square roots, floors, trigonometry. No store, no install, no workspace decisions. Battery included.

Also lives here: random, json, datetime — the everyday toolkit.

Third-party library — fetched from PyPI

matplotlib is not inside Python. Someone wrote it, packaged it, and published it; pip must fetch and install it into a project before import matplotlib works. Meeting 2 is entirely about doing that correctly.

Same shelf, other kits: numpy, pygame, requests.

One word that does neither: import is a Python statement in your code — it opens a box that is already installed. It never downloads anything. Downloading is pip's job; importing is yours.

Meeting 1 · Activity 1 — the handmade solution

Newton's method — guess, then improve the guess

# The "guess and check" method (SG Activity 1)
x = 25
guess = x / 2          # first guess: 12.5
for _ in range(10):    # improve it ten times
    guess = (guess + x / guess) / 2
print(f"Manual: {guess}")

The improvement rule: take the average of your guess and x / guess. If the guess is too big, x / guess is too small — the average lands closer to the truth.

Meeting 1 · Activity 1 — the library solution

The NASA kit, in two lines

import math
print(f"Library: {math.sqrt(25)}")

Output: Library: 5.0. No loop, no guesses, no rounding anxiety. math is the standard library — already installed with Python, so no pip and no workspace needed (slide 7).

What you did NOT do

  • derive the algorithm
  • choose how many iterations are enough
  • test it against edge cases (0? 0.25? a million?)
  • maintain it when Python changes

Someone else did — a long time ago, and millions of programs have stress-tested it since.

The SG's claim, kept honest: the library version is shorter, optimized, and vetted — but "optimized" and "vetted" are claims this meeting will test, not just repeat. That test is Activity 2.

Meeting 1 · Activity 2 — the Performance Face-off SG17 · 15-min activity

PREDICT Then race — but gate it on accuracy first

# THE FIX: run Newton until it CONVERGES (the SG's fixed
# 10 rounds stops at ~1168.24 for this input — wrong by 57!)
def manual_sqrt(x):
    guess = x / 2
    while abs(guess*guess - x) > 1e-6:
        guess = (guess + x / guess) / 2
    return guess

# --- ACCURACY GATE FIRST: a race between wrong
# answers proves nothing ---
print("Manual Result: ", manual_sqrt(number))
print("Library Result:", library_sqrt(number))

# --- THEN the 100,000-round race ---
manual_time  = timeit.timeit(lambda: manual_sqrt(number),  number=repeats)
library_time = timeit.timeit(lambda: library_sqrt(number), number=repeats)

The trap in the SG's original code

Ten fixed rounds converges for 25 — and quietly fails for 1,234,567: it stops at 1168.24, wrong by 57 (≈5%). The SG's sample output prints a far more precise answer than its code produces. Fixed round counts that worked on small numbers do not scale — run to convergence instead (13 rounds here).

Meeting 1 · Activity 2 — reading the result honestly

The winner — and what the race really proves

Why is math.sqrt faster?

Carefully stated: Python's math module wraps the C standard library's square-root function — compiled, optimized machine code that Python calls into. Your Newton loop is ten-plus rounds of Python bytecode per answer; math.sqrt is one call into compiled code. Not "the CPU just does it" — Python still makes the call; the C layer is what makes the call cheap.

Five honest takeaways

  • A good library saves implementation time
  • Established libraries are often highly optimized
  • Shorter ≠ faster — the claim needs the stopwatch
  • Libraries are not automatically correct or secure — you still verify (Meeting 2's accuracy gate habit)
  • Benchmarks depend on machine and implementation — our machine said 18×; the SG's example said 9.9×; both are true stories
And the stopwatch itself: timeit's own docs warn that other running programs can interfere with timings. Treat every race result as evidence, not law — same habit as the accuracy gate.

Meeting 2 · How do we integrate libraries responsibly?

A good tool needs a proper workspace

You chose the tool. Now — where does it install?

matplotlib is not in Python (slide 7). pip must fetch it. But into what? Your computer has one Python — and many projects, each with its own needs, versions, and kit combinations.

Install everything into the one shared Python and you get a slow-motion collision: every project shares one shelf.

Meeting 2 · The .venv workspace — and its honest boundary

What the workspace does — and what it does not

It DOES isolate between projects

.venv = a private Python + a private package shelf, inside the project folder. Install matplotlib there and only that project sees it. Your other projects, and the computer's main Python, never notice. Private workspaces so kits don't collide across projects.

It does NOT fix within-project conflicts

If two libraries in the SAME project demand different versions of the same tool (slide 19), the workspace cannot satisfy both — there is one shelf inside the project. That jam needs investigation and a decision, not a new folder.

The sentence to keep: virtual environments separate projects from each other. They do not automatically resolve incompatible requirements inside one project. (You will reason through exactly this in Mission L-1's Traffic Jam phase — and the honest limits of that practice are stated there too.)

Meeting 2 · Give your project its toolbelt — Windows + VS Code

Three moves, one workspace

1 · Create the workspace (in the project folder, VS Code terminal: Ctrl + `)

py -m venv .venv

A .venv folder appears in the Explorer — the project's private shelf.

2 · Lock it in

Click the popup bottom-right (Yes) — or Ctrl + Shift + P → "Python: Select Interpreter" → the one with .venv. The status bar now shows the workspace's Python.

3 · Trust, then verify

Open a new terminal (it picks up the lock-in) and check the (.venv) prefix. The terminal, the interpreter, and pip must all point at the same workspace — the next slide proves it.

Meeting 2 · Check before you install

Four lines that prevent every "wrong environment" bug

# 1 · which Python is this terminal using?
python -c "import sys; print(sys.executable)"

# 2 · does pip belong to that same Python?
python -m pip --version

# 3 · fetch the kit — into THIS workspace
python -m pip install matplotlib

# 4 · prove where it landed
python -m pip show matplotlib

Line 4's Location: must contain .venv — that is the proof.

The relationship that matters

The selected interpreter and pip must be the same environment. python -m pip guarantees it: pip runs inside the Python you called. Bare pip can belong to a different Python — and installs onto the wrong shelf.

Check, don't assume

A version check like pip --version diagnoses — it tells you pip exists and where. It cannot repair a missing or broken Python installation: if py itself is not recognized, no command fixes it in class — that is a teacher/IT decision. When something feels wrong, run line 1 and look.

Meeting 2 · The dependency traffic jam

Two libraries, one tool, two demands

Installing both demands breaks one library or the other — a dependency conflict. A new .venv gives this project a shelf, but the two demands still collide on it. The professional moves: read both libraries' docs for version flexibility · check for a newer release · find an alternative to one library · decide and document.

Meeting 2 · From Python code to a matplotlib graph

Read the template before you type it

import matplotlib.pyplot as plt

# Sample research data — ILLUSTRATIVE
hours = [0, 1, 2, 3, 4, 5]
bacteria_count = [100, 150, 300, 650, 1200, 2500]

plt.plot(hours, bacteria_count, marker='o', color='green')

plt.title("Bacteria Population Growth")
plt.xlabel("Time (Hours)")
plt.ylabel("Number of Bacteria")
plt.grid(True)

print("Generating graph...")
plt.savefig("bacteria_growth.png", dpi=150)  # save FIRST
plt.show()                                    # then display

What each block does

  • import … as plt — open the kit, give it a short name
  • the lists — x values, y values, same length
  • plot + marker + color — the line and its visible points
  • title / labels / grid — a graph a stranger can read
  • savefig → show — evidence first, celebration second
Abstraction, again: you call plt.plot and never see how pixels are drawn — the library's interface does the complex part. You met this idea as OOP pillar #4; here it earns your graph. Reading happens now; the typing happens in L-1.

Meeting 2 · Save, inspect, and explain

The graph is not done until it testifies

Why save before show

plt.show() hands control to the window — and closing that window can clear the figure. savefig first means the PNG exists no matter what happens to the window. Order is evidence.

Result on disk: bacteria_growth.png — 960×720 pixels (dpi 150), openable without Python, submittable to the LMS.

What the curve says

The count goes ×25 in five hours. Each hour it roughly doubles (1.5×, 2.0×, 2.2×, 1.9×, 2.1×). The largest proportional increase happens between hours 2 and 3 (about 2.17×). However, the largest absolute increase happens between hours 4 and 5 (+1,300 bacteria). The Biology team's sentence: the colony grows faster and faster — exponential-style growth. That sentence is the "explain" in the mission.

Check the whole chain, then claim the rank: (.venv) prefix → Generating graph... with no red text → window shows title, labels, points, grid → PNG in the Explorer. Then you may say what it proves — evidence is your rank, in that order.

Meeting 2 · Choose your tools responsibly

A package manager trusts you to look

Identity — check the name

PyPI is open to everyone. A mistyped or look-alike package name can be a Trojan horse — SG 17's own warning. Check the package's page and documentation before installing; prefer established, relevant kits (matplotlib: millions of users, real docs).

Licensing — "open source" is not "no rules"

Some kits ask for credit (the MIT license does), others restrict commercial use. Before reusing a library in a project, check the license — school work included, because the habit is the point.

The discipline rule from Mission L-1: install only what the task needs — one clean delivery per mission. Every extra package is more download time, more update risk, more shelf you cannot explain. If you cannot say why a package is on the shelf, it should not be.
